## Where the manager fits

The manager sits between raw logger output and the tools you use for analysis.
It can watch folders, download completed sessions from Wi-Fi loggers, run the
BODAQS preprocessing pipeline, and write the results into a local library.

It does not require a cloud account, database server, phone app, or Python
environment for normal use.

<CardGrid>
  <Card title="Logger session">
    A completed ride or test recorded by the BODAQS logger. For local-folder
    sources, this is normally a `.zip` archive containing matching logger data
    and sidecar metadata files.
  </Card>
  <Card title="Source">
    One place sessions come from. A source can be a local archive folder or a
    Wi-Fi logger. Each source has its own settings, bike profile, note template,
    and target library.
  </Card>
  <Card title="Library">
    The destination for processed sessions. A library contains run artifacts,

  </Card>
  <Card title="Import run">
    A batch of work performed by the manager. Even a single imported session is
    written into a run folder so the result has provenance and can be found
    again later.
  </Card>

## The two tabs

The Import Manager has two main areas:

- **Manager** is for everyday operation: checking sources, importing now,
  starting or stopping watch mode, editing source settings, and reviewing
  status.
- **Provision** is for creating or extending the setup: adding libraries and
  sources, choosing source type, and setting the initial target library.

The setup guide walks through the first provisioning pass. In normal use, most
of your time will be on the **Manager** tab.

## Recommended daily workflow

For a local archive folder source, the usual rhythm is:

<Steps>
  1. Record a session on the logger.
  2. Export or copy the completed logger archive to the source `inbox/` folder.
  3. Open the Import Manager.
  4. Select **Import Now**, or start the watcher and leave the app running.
  5. Check the status log for imported, deferred, or failed sessions.
  6. Open the target library from Jupyter Lab, data.syn.bike, or another BODAQS
     analysis tool.
</Steps>

For a Wi-Fi logger source, the rhythm is similar, except the manager downloads
the completed session from the logger instead of reading a `.zip` file from
`inbox/`.

<Aside type="caution" title="Completed files only">
  The manager expects complete sessions. Do not import a file that is still
  being copied, and do not ask the manager to download from a logger that is
  actively recording.
</Aside>

## Folder layout

By default, the app creates a local-first layout under your user folder:

```text
BODAQS/
  libraries/
    <library>/
  sources/
    <source>/
```

You can choose other root folders during setup. The important idea is that
libraries and sources are separate:

- source folders hold inputs and per-source settings
- library folders hold processed outputs

### Source folders

A typical source folder looks like this:

```text
<source>/
  import_source.json
  bike/
  settings/
  notes/
  fit/
  inbox/
  done/
  failed/
  staging/
```

The manager owns the workflow folders:

- `inbox/` receives new local archives
- `staging/` is temporary working space during import
- `done/` receives successfully imported local archives
- `failed/` receives local archives that could not be imported

The source configuration folders are intended to be readable and editable:

- `bike/` contains the source bike profile
- `settings/` contains preprocessing and event-schema settings
- `notes/` contains the optional session-note template and preset
- `fit/` contains optional `.fit` files used for enrichment

### Library folders

A typical library looks like this:

```text
<library>/
  runs/
  library/
  syn/
  library_definition.json
```

The `runs/` folder is the main processed output. Each import creates a run
folder, and each run contains one or more processed sessions.

The `library/` folder stores library-level state such as catalogs, notes, and
other metadata. The `syn/` folder is used only when data.syn.bike export is
enabled for that library.

## Manager tab

<Flag src="/src/assets/pics/import-manager.png" alt="Import Manager window">
The **Manager** tab is the operational center of the app. It shows configured
libraries and sources, exposes import actions, and writes a status log as work
is performed.
</Flag>

### Library list

The library list shows the libraries managed by the app. Each library has a
display name, an internal library ID, a folder path, and a **Syn Export**
setting.

Use **Syn Export** when you want new imports into that library to produce
data.syn.bike-compatible CSV outputs. The setting affects future imports. It
does not automatically rebuild exports for sessions that were already imported.

### Source list

The source list shows the configured data sources. Important columns include:

- **Enabled**: whether the source is included in **Import Now** and watch mode
- **Source Name**: the human-readable name shown in the manager
- **Type**: local archive folder or Wi-Fi logger
- **Status**: the most recent runtime status reported by the manager
- **Target Library**: where sessions from this source are processed
- **Bike Name**: the bike profile currently associated with the source
- **Attach Note**: whether draft setup notes are created for future imports

You can toggle **Enabled** and **Attach Note** directly in the source table.

### Source context menu

Right-click a source to open actions for that source. Depending on the source
type, the menu can include:

- edit the bike profile
- edit the note profile
- copy bike or note settings from another source
- change the target library
- view source details
- edit Wi-Fi settings
- check logger status
- request logger upload mode
- validate the source
- rename or remove the source

Stop watch mode before editing source settings. The manager will also block
some editing actions while the watcher is active.

## Import Now and watch mode

<CardGrid>
  <Card title="Import Now">
    Scans enabled sources once. Use this when testing a new source, importing a
    small number of files, or checking whether a failed setup has been fixed.
  </Card>
  <Card title="Start Watch">
    Keeps the manager running and checks enabled sources repeatedly. Use this
    once the source and library setup is stable.
  </Card>
</CardGrid>

**Import Now** is the safer first test for a new setup. Once you can import a
known-good session manually, watch mode is useful for unattended folder or
logger workflows.

When watch mode is running, avoid changing source settings, moving source
folders, or editing bike/profile files.

## Start at login and tray behavior

The manager can save a start-at-login preference. On Windows this creates a
per-user startup entry, so administrator access is not required.

When the app starts at login, it uses the saved app configuration and can start
the watcher automatically. If the window is hidden, use the tray icon to reopen
or quit the manager.

<Aside type="note" title="One app instance">
  The manager prevents two copies from running against the same app
  configuration. This avoids duplicate watchers, duplicate tray icons, and
  competing edits to the same settings files.
</Aside>

## Adding libraries and sources

<Flag src="/src/assets/pics/import-mgr-provisioning.png" alt="Import Manager provisioning tab">
Use the **Provision** tab when you need to add another destination library or
another data source. You do not need to repeat the whole first-run setup.
</Flag>

Add another library when you want a separate destination for processed sessions.
Common reasons include:

- a different rider
- a different bike
- a separate test program
- a clean library for experiments

Add another source when sessions arrive from a different place or need different
settings. Common reasons include:

- another logger
- another bike profile
- another folder watched by the manager
- different note defaults
- a different target library

Each source targets one library, but multiple sources can target the same
library.

## Local archive folder sources

Choose **Local archive folder** when completed sessions are copied into a
folder as archives.

The import flow is:

<Steps>
  1. Put a completed `.zip` session archive in the source `inbox/` folder.
  2. The manager waits until the archive appears stable.
  3. The archive is extracted into `staging/`.
  4. The manager validates the session files.
  5. The BODAQS preprocessing pipeline runs.
  6. Processed outputs are written to the target library.
  7. The archive moves to `done/` on success or `failed/` on failure.
</Steps>

The archive should contain one logger session. The data file and sidecar file
inside the archive must describe the same session.

## Wi-Fi logger sources

Choose **Wi-Fi logger** when the manager should talk directly to a BODAQS logger
on the local network and download completed sessions.

The logger must be:

- powered on
- connected to the same local network as the computer
- not actively logging
- in upload mode, or able to enter upload mode

### Discovery and logger identity

The manager identifies a Wi-Fi source by logger ID. The network address is only
where the logger can currently be reached.

Use discovery where possible. Discovery can find a logger even if its IP address
has changed. If discovery is blocked by the network, firewall, VPN, or guest
network isolation, you can use a manual address.

Manual addresses look like:

```text
http://192.168.1.42
```

### Fixed address mode

Fixed logger addresses are optional. Leave fixed address mode off when the
logger is normally discoverable on the network. In that mode, the manager keeps
the logger ID but does not permanently save a discovered IP address.

Turn fixed address mode on only when the logger has a stable address and
discovery is unreliable or unavailable. If a remembered fixed address stops
working, the manager can still try mDNS discovery as a fallback.

### Upload mode

Upload mode protects active logging. A logger should not transfer files while it
is recording.

Use **Check Logger** to confirm the selected source reaches the expected logger
and to see whether upload mode is active. Use **Request Upload Mode** if the
logger is reachable but not yet accepting transfers.

If the manager cannot put the logger into upload mode, use the logger controls
directly, then return to the manager and check again.

### Remote cleanup

After a successful Wi-Fi import, the manager can acknowledge the imported
session to the logger. Depending on the source settings, the logger can:

- keep the remote files
- move them to an uploaded/archive area
- delete them

Start conservatively. Keep remote files until you are confident that the
library outputs are complete and the workflow is doing what you expect.

## Bike profiles

<Flag src="/src/assets/pics/bike-profile-complete.png" alt="Completed bike profile editor">
Each source has its own bike profile. This lets different bikes, riders, or
test programs use different geometry and travel transformations while still
importing into the same library if desired.
</Flag>

The bike profile controls how logger signals are interpreted during
preprocessing. It can include:

- bike name and descriptive details
- wheel travel and suspension travel values
- front suspension geometry, including head angle
- rear wheel travel lookup table
- normalization ranges used by downstream analysis and exports

### Rear wheel lookup table

The rear wheel lookup table maps rear suspension movement to rear wheel travel.
At minimum, it needs a zero-travel point and a full-travel point. Additional
points let the profile describe a non-linear suspension curve.

The manager can edit the table in the bike profile editor. You can also copy a
bike profile from another source if two sources use the same bike.

### Front suspension

Fork movement is measured along the fork, but front wheel travel is usually
treated as vertical wheel movement. The head angle lets the manager derive that
vertical component during preprocessing.

### Editing JSON directly

Bike profiles are JSON files inside the source `bike/` folder. Direct editing
is possible, but keep exactly one active bike profile in that folder. Store old
or experimental versions elsewhere.

## Note profiles and draft setup notes

<Flag src="/src/assets/pics/edit-note-profile.png" alt="Edit note profile">
The note profile controls which setup-note fields are created for imported
sessions and what default values they start with.
</Flag>

A source can attach a draft setup note to each imported session. This is useful
for recording settings such as:

- rider
- bike
- fork pressure and clicks
- shock pressure and clicks
- sag
- tyres
- trail or test conditions
- comments

Draft notes are intentionally marked as drafts. They are meant to be reviewed
and edited later, because the defaults may not exactly match the setup used for
that session.

Use **Attach Note** in the source list to turn draft note creation on or off for
future imports from that source.

## FIT enrichment

If the source preprocess settings enable FIT enrichment, the manager looks in
the source `fit/` folder for matching `.fit` activity files.

Rules of thumb:

- copy FIT files fully before importing sessions
- FIT files are read in place
- FIT files are not moved or deleted by the manager
- if multiple FIT files overlap a session, the best overlap is preferred
- if matching fails, the import can still continue without FIT enrichment

FIT enrichment is optional. The core logger import does not depend on it.

## data.syn.bike exports

If **Syn Export** is enabled for the target library before import, the manager
writes data.syn.bike-compatible outputs into:

```text
<library>/syn/
```

<Flag src="/src/assets/pics/synoutputs.png" alt="data.syn.bike export outputs">
The `syn/` folder contains exported CSV files, helper text files, and export
metadata for sessions imported while export was enabled.
</Flag>

The helper text files show the settings to enter manually when uploading to
data.syn.bike. This is useful because the export is shaped for data.syn.bike,
but the website still expects some setup information to be entered by the user.

Old sessions are not backfilled automatically when you turn **Syn Export** on.
Re-import or rebuild exports separately if you need outputs for earlier
sessions.

## Validation and status messages

Use **Validate** after editing source files or adding a new source. Validation
checks whether the manager can read the source configuration and related
settings.

The status log is the first place to look when something unexpected happens. It
reports source validation results, import counts, Wi-Fi logger checks, watcher
snapshots, and common failures.

For local archive sources, a typical import status includes:

- sessions seen
- sessions imported
- sessions deferred because the file is not settled yet
- sessions failed

For Wi-Fi sources, status can also report upload mode, logger identity, and
network errors.

## Removing a source

Removing a source from the manager removes it from the app configuration. It
does not delete:

- the source folder
- archived input files
- failed imports
- bike profiles
- note templates
- target library data

This makes removal safe. It stops the manager from using that source, while
leaving the files available if you need them later.

## Troubleshooting

### A local archive stays in inbox

Check that:

- the file is a `.zip`
- the file copy has finished
- the source is enabled
- the watcher is running, or you selected **Import Now**
- the archive contains a valid completed logger session

### A local archive moved to failed

Open the status log and inspect the source `failed/` folder. Common causes
include:

- invalid or incomplete archive contents
- bike profile validation errors
- preprocess profile validation errors
- event schema validation errors
- the target library path is unavailable
- preprocessing failed

### A Wi-Fi logger is not discovered

Try:

- confirm the logger and computer are on the same network
- confirm logger Wi-Fi is on
- confirm the logger is in upload mode
- disable VPNs that may block local discovery
- check whether guest-network isolation is enabled
- try a manual address with fixed address mode

### A Wi-Fi source reports the wrong logger

The manager compares the reachable logger ID with the logger ID saved in the
source. If they do not match, it refuses to import. Check that the source points
to the intended logger, especially if a fixed address is being used.

### A source says waiting for upload mode

The logger is reachable, but it is not currently accepting transfers. Put the
logger into upload mode, then run **Check Logger** or **Import Now** again.

### No data.syn.bike files were written

Check that:

- **Syn Export** was enabled on the target library before import
- the imported session contains compatible signals
- the bike profile includes the needed travel and normalization information
- the import completed successfully

### No draft note was attached

Check that:

- **Attach Note** was enabled before import
- the source `notes/` folder contains a valid note template
- the source `notes/` folder contains a valid bike setup preset
- the note preset matches the template

## Safe operating habits

- Test a new source with **Import Now** before using watch mode.
- Stop watch mode before editing source settings.
- Keep one active bike profile per source.
- Keep old settings outside the active `bike/`, `settings/`, and `notes/`
  folders.
- Keep raw logger archives until you have checked the processed library output.
- Use conservative Wi-Fi cleanup settings until the workflow is proven.
- Back up important libraries like any other project data.
